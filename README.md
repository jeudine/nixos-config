# nixos-config

Flake-based NixOS configuration for a single headless machine: the host `server`.

## Layout

| File | Purpose |
| --- | --- |
| `flake.nix` | Inputs (nixpkgs 26.05, [claude-code-nix](https://github.com/sadjow/claude-code-nix), [rust-overlay](https://github.com/oxalica/rust-overlay)) and the `nixosConfigurations.server` output |
| `configuration.nix` | The actual system config: bootloader, networking, users, services, packages |
| `nfs-clients.example.nix` | Template for the NFS client list. The real one is kept out of this repo, at `~/nixos-private/nfs-clients.nix` |
| `hardware-configuration.nix` | Generated by `nixos-generate-config`; filesystems, kernel modules, CPU. Do not edit by hand |
| `flake.lock` | Pinned revisions of all inputs |
| `update.sh` | Update inputs, rebuild, commit the new lock |
| `install.sh` | Set up a machine: check prerequisites, rebuild, create the symlinks |
| `workspace/CLAUDE.md` | Agent instructions for `/workspace`, symlinked there as `/workspace/CLAUDE.md` |

## What the system provides

- **Boot**: systemd-boot on UEFI.
- **Storage**: btrfs, a `tank` filesystem with `data` and `workspace` subvolumes, scrubbed monthly. See [Storage (btrfs)](#storage-btrfs).
- **Host**: `server`, timezone `Europe/Zurich`, `x86_64-linux`.
- **User**: `julien`. No password is set here — set one with `passwd` or add `users.users.julien.openssh.authorizedKeys.keys`.
- **NFS**: `/data` and `/workspace` exported over NFS v3 and v4 to the LAN, per the client list in `~/nixos-private/nfs-clients.nix`. See [NFS](#nfs).
- **SSH**: `openssh` enabled with password authentication disabled, so key-based login only.
- **Tailscale**: `tailscaled` running, so SSH and NFS are also reachable over the tailnet. See [Tailscale](#tailscale).
- **mDNS**: `avahi` publishing addresses, so the box is reachable as `server.local`.
- **Nix**: `nix-command` and `flakes` experimental features enabled.

## Usage

Clone somewhere on the machine (this repo lives in `~/nixos-config`, not `/etc/nixos`):

```bash
git clone <this-repo> ~/nixos-config
cd ~/nixos-config
```

On a new machine, run the installer. It checks that `~/nixos-private/nfs-clients.nix`
and the `tank` filesystem exist, rebuilds (enabling flakes for that one run, since a
fresh install lacks them), then creates the symlinks listed in its `LINKS` array:

```bash
./install.sh               # rebuild and link
./install.sh --no-rebuild  # only (re)create the symlinks
```

If `nfs-clients.nix` is missing it is created from the example and the script stops
so you can fill it in. A file already sitting where a link goes is removed if it is
identical to the repo copy, and otherwise renamed to `<name>.bak.<timestamp>`.
Re-running is harmless. To add a link, add a `"link:target"` entry to `LINKS`, with the
target relative to the repo.

`/workspace/CLAUDE.md` points to `/home/julien/nixos-config/...`, and NFS clients
resolve symlinks on their own side, so over NFS the link appears broken. It works
on the server, where the agents run.

Apply the configuration:

```bash
sudo nixos-rebuild switch --flake .#server --impure
```

Test without making it the boot default:

```bash
sudo nixos-rebuild test --flake .#server --impure
```

Build only, to check that it evaluates:

```bash
nixos-rebuild build --flake .#server --impure
```

## Storage (btrfs)

`configuration.nix` mounts two subvolumes from the btrfs filesystem labelled
`tank`: `data` at `/data` and `workspace` at `/workspace`. Both sit at the top
level of the filesystem, not inside each other.

To create them, first find the partition to use. **Everything on it will be
erased.**

```bash
lsblk -o NAME,SIZE,FSTYPE,LABEL,MOUNTPOINT
```

Then, replacing `/dev/sdX1` with that partition (e.g. `/dev/sdb1`,
`/dev/nvme0n1p3`):

```bash
nix shell nixpkgs#btrfs-progs    # btrfs tools aren't installed until the first rebuild
sudo mkfs.btrfs -L tank /dev/sdX1
sudo mkdir -p /mnt
sudo mount /dev/disk/by-label/tank /mnt
sudo btrfs subvolume create /mnt/data
sudo btrfs subvolume create /mnt/workspace
sudo umount /mnt
sudo nixos-rebuild switch --flake .#server --impure
```

`mkfs.btrfs` refuses to overwrite a partition that already holds a filesystem.
If it does, and you are sure the data can go, clear it with
`sudo wipefs -a /dev/sdX1` and run `mkfs.btrfs` again.

The partition only appears in the `mkfs.btrfs` step: after that everything
goes through the `tank` label, which is also what `configuration.nix` mounts.
No other change to the config is needed. The label and the subvolume names
must match the `fileSystems` entries there, and the mount points are created
automatically.

## NFS

Both subvolumes are exported over NFS, v3 and v4, to the server's own LAN only.
`configuration.nix` opens the ports they need in the firewall.

**Who may mount what is listed in `~/nixos-private/nfs-clients.nix`**, one `rw`
and one `ro` list per export. That file is deliberately outside this repo, so
the addresses are not published; [`nfs-clients.example.nix`](nfs-clients.example.nix)
shows the format. `configuration.nix` reads it by absolute path and turns the
lists into `/etc/exports`, so adding a machine means adding its address there
and running `sudo nixos-rebuild switch --flake .#server --impure`:

| Client | `/data` | `/workspace` |
| --- | --- | --- |
| hosts in the export's `rw` list | read-write | read-write |
| hosts in its `ro` list | read-only | read-only |
| anything else | no access | no access |

An export whose `ro` list is empty is reachable only by the hosts named in `rw`;
everyone else is refused with `access denied by server`. Where a host appears in
`rw` and is also covered by a subnet in `ro`, the single-host entry wins:
`exports(5)` ranks specifications as single host, then IP network, then
wildcard, then netgroup, then `*`, and the most specific match applies
regardless of the order they are written in.

The `rw` addresses should be DHCP reservations on the router, or statically
configured. If an address changes hands, write access follows the address, not
the machine.

Mount one by hand from a client:

```bash
sudo mount -t nfs server.local:/workspace /mnt
```

From macOS, **use v3 and mount outside your home directory**:

```bash
sudo mkdir -p /System/Volumes/Data/mnt/workspace
sudo mount -t nfs -o vers=3,resvport,soft,timeo=30,retrans=3,nobrowse \
  server.local:/workspace /System/Volumes/Data/mnt/workspace
```

Every option there earns its place:

- **`vers=3`** because macOS does not reliably complete an NFSv4 handshake. It
  connects to 2049 and then stalls.
- **`resvport`** because the exports carry the default `secure` option, which
  requires a source port below 1024.
- **`soft,timeo=30,retrans=3`** so a stuck mount returns an error. NFS mounts
  are *hard* by default: anything touching the path blocks uninterruptibly, and
  a Mac freezes rather than failing.
- **`nobrowse`**, plus a mount point outside `/Users`, to keep Finder and
  Spotlight from indexing the share. Indexing a wedged mount is what turns one
  stuck process into a frozen desktop.

`/mnt` cannot be created on macOS: the system volume is read-only and sealed.
`/System/Volumes/Data/mnt` is the writable equivalent.

Unstick a hung mount with `sudo umount -f <path>`, or
`sudo diskutil unmount force <path>`.

Finder can do it too: Go → Connect to Server → `nfs://server.local/workspace`.

Or persistently, on a NixOS client:

```nix
fileSystems."/workspace" = {
  device = "server.local:/workspace";
  fsType = "nfs";
  options = [ "x-systemd.automount" "noauto" ];
};
```

Things worth knowing:

- **Both v3 and v4 are served.** v4 alone would need only TCP 2049, but the
  macOS client stalls on it, so v3 is enabled too. v3 needs rpcbind (111) plus
  mountd, statd and lockd, which pick random ports by default;
  `mountdPort`/`statdPort`/`lockdPort` pin them to 4002/4000/4001 so the
  firewall rules can be exact. Linux clients still negotiate v4 by default.
- **Read-write clients are mapped to `julien`.** NFS identifies users by
  numeric UID, and a client's numbering need not match the server's — macOS gives
  its first user 501, where `julien` here is 1000. `all_squash,anonuid=1000,anongid=100`
  on every `rw` entry maps each incoming user, `root` included, to `julien`.
  Files they create are owned by `julien:users` on the server.
- **`fsid=` is mandatory here.** `/data` and `/workspace` are two subvolumes of
  one btrfs filesystem, so they share a UUID; without distinct `fsid` values
  the server cannot tell the exports apart.
- **Ownership is set declaratively** by `systemd.tmpfiles.rules`, so a
  reformatted filesystem does not come back root-owned and unwritable.

Check what is exported, and who is connected:

```bash
sudo exportfs -v
sudo ss -tnp 'sport = :2049'
```

## Tailscale

`services.tailscale` runs `tailscaled`, and `openFirewall` opens UDP 41641 so
peers can reach the server directly instead of through a DERP relay. Nothing
else changes in the firewall: SSH (22) and the NFS ports are already open on
every interface, `tailscale0` included.

Join the tailnet once after the first rebuild. The login is kept in
`/var/lib/tailscale`, so it survives reboots and rebuilds:

```bash
sudo tailscale up
tailscale ip -4            # the server's 100.x address
```

Then, in the Tailscale admin console, **disable key expiry** for this machine,
or it drops off the tailnet when its key expires (180 days by default).

**SSH** is the normal OpenSSH server, reached at the tailnet address or the
MagicDNS name (`ssh julien@server`, or whatever name the admin console shows).
Tailscale SSH (`tailscale up --ssh`) is not used, so the usual key-only login
applies.

**NFS** authorises clients by source address, and over the tailnet that source
is the client's own 100.x address, not its LAN one. Add that address to the
export lists in `~/nixos-private/nfs-clients.nix`, then rebuild:

```nix
rw = [
  "192.168.1.50" # some-client, on the LAN
  "100.101.102.103" # some-client, over Tailscale
];
```

Tailscale addresses are stable per machine, so they suit `rw` better than DHCP
leases do. Listing the whole tailnet range, `100.64.0.0/10`, would admit every
device on it. Mount with the same options as on the LAN, swapping the host:

```bash
sudo mount -t nfs -o vers=3,resvport,soft,timeo=30,retrans=3,nobrowse \
  100.101.102.103:/workspace /System/Volumes/Data/mnt/workspace
```

Use the server's 100.x address (or its MagicDNS name) here, not `server.local`:
mDNS does not cross the tailnet.

## Updating

`update.sh` wraps the update-rebuild-commit cycle. It refuses to run with a dirty
working tree, and does nothing if `flake.lock` comes back unchanged.

```bash
./update.sh                # update every input
./update.sh claude-code    # update a single input
```

The script derives the flake attribute from `hostname`; override it with
`HOST_OVERRIDE=server ./update.sh` if the machine's hostname ever differs from
the `nixosConfigurations` name.

Once it has finished, the script checks how full `/` is. At 85% or more, it
deletes every system generation except the newest 5, the same number the
systemd-boot menu keeps, and then collects garbage from the Nix store. Both
numbers can be overridden:

```bash
DISK_THRESHOLD=90 KEEP_GENERATIONS=3 ./update.sh
```

To roll back an update:

```bash
git revert HEAD
sudo nixos-rebuild switch --flake .#server --impure
```

Previous generations are also available from the systemd-boot menu, or via
`sudo nixos-rebuild switch --rollback`.

## Adding a new machine

1. Run `nixos-generate-config --no-filesystems` on the new host and copy its
   `hardware-configuration.nix` into a per-host directory.
2. Add a matching `nixosConfigurations.<hostname>` entry in `flake.nix`.
3. Move anything shared out of `configuration.nix` into a common module.
